# 기술 문서를 이해하기 쉽게 다듬기

## 먼저 독자와 목적을 정하기

초안과 요청에서 독자가 누구이고 무엇을 알아야 하는지 파악하라. 맥락이 충분하면 다시 묻지 마라. PM·운영자·개발자가 함께 읽는 업데이트라면 핵심 변경과 영향을 먼저 설명하고 배포 담당자의 세부 확인 사항을 따로 모아라. 사용자가 구조를 유지하라고 요청하면 그 범위 안에서 다듬어라.

- 업데이트·릴리즈 노트: 기준 버전과 핵심 변경 → 주요 변경의 이유와 영향 → 적용 전 확인 사항 → 기타 수정과 개발 중인 항목 → 필요한 상세 이력 순서를 기본으로 삼아라.
- 개발 경험 글: 실제 문제 → 원문에 있는 제약·선택 이유 → 구현 방법 → 확인한 결과와 남은 한계를 연결하라.
- 기능 설명: 무엇을 할 수 있는지 → 언제 쓰는지 → 어떻게 동작하는지 → 필요한 조건과 제약을 설명하라.

정해진 목차를 빈칸까지 채우지 마라. 개발 중인 항목이 없으면 빈 절을 삭제하라. 적용 전에 반드시 알아야 할 변화는 글 앞에도 짧게 알리고, 구체적인 확인 방법은 한곳에 모아라.

## 문장보다 정보의 순서를 먼저 고치기

1. 날짜, 버전, 설정 기본값, 지원 범위, 예외, 제약, 확인 상태를 먼저 파악하라. 원문 안에서 충돌하는 설명은 임의로 해결하지 말고 확인이 필요한 지점으로 남겨라.
2. 각 절의 첫 문장에서 핵심 변경과 적용 조건을 함께 알려라. 변경 사항 → 필요한 배경·동작 → 사용·운영 영향 순서로 연결하라. 원문에 이유가 없으면 이유를 추측하지 마라. 작은 수정은 한 문장으로 설명해도 된다.
3. 문단 하나가 한 가지 질문에 답하게 하라. 이해에 필요한 이유와 조건은 남기고 같은 결론을 바꿔 말한 문장, 당연한 설명, 문서 편집 과정에 관한 설명을 줄여라.
4. 요약·본문·표의 역할을 나눠라. 요약에는 주요 결론, 본문에는 설명, 표에는 실제 비교나 대응 관계를 담아라. 값이 모두 같은 비교표는 기준과 공통 결과를 요약하되, 고유한 변경 이력과 추적 정보는 부록에 보존하라.
5. 용어를 처음 썼다는 이유만으로 정의를 붙이지 마라. 독자의 배경지식을 고려해, 설명이 없으면 다음 내용을 이해하기 어려운 용어만 필요한 지점에서 짧게 설명하라. 예를 들어 파이프라인 사용자를 위한 업데이트에서는 중복 제외 노드를 설명하다가 노드의 일반적 정의로 되돌아가지 마라. 긴 용어집을 먼저 읽도록 요구하지 마라. 같은 대상을 번역어·별칭·내부 코드로 번갈아 부르지 마라.

## 핵심을 먼저 말하되 설명을 반복하지 않기

- 제목에는 변경 내용이나 사용자에게 미치는 영향을 담아라. '내부 API 키 관리'보다 '내부 API 키를 기본 6시간마다 갱신합니다'처럼 구체화할 수 있다. 자연스러운 명사형 제목도 허용하라.
- '실행에 성공하면 중간 파일을 삭제합니다'처럼 조건을 결론 가까이에 두어라. 두괄식으로 줄이면서 성공·실패, 일부·전체, 기본값·선택 설정을 지우지 마라.
- 제목에서 알린 변경을 첫 문장에서는 적용 시점·대상·동작으로 구체화하라. 다음 문장은 이유나 영향을 더하라. 제목·첫 문장·다음 문장에서 같은 결론을 바꿔 말하지 마라.
- 독자가 이어서 궁금해할 내용을 설명하라. 단순 오류 수정에는 배경·주의·마무리를 억지로 붙이지 마라. 중요한 조건의 재안내와 의미 없는 반복을 구분하라.
- 주의 사항에는 원문에서 확인한 행동을 적어라. '주의가 필요합니다'로 끝내지 말고 무엇을 확인할지 알려라. '사용하지 않기로 했다면 사용할지 결정해 주세요'처럼 결정을 되묻지 마라. 절차가 불명확하면 조치를 지어내지 마라.
- 다음 절로 넘어가기 위한 연결 문장만 있다면 삭제하라. 문단을 연결하려고 관계없는 변경 사이에 인과관계를 만들지 마라.

## 문체와 설명의 구체성

담백한 '합니다'체를 기본으로 써라. 사용자가 다른 격식을 원하면 따르라. 짧게 쓸 때도 조사와 동사를 생략해 독자가 관계를 복원하게 만들지 마라. 직접 연결되는 변경 동작과 효과는 한 문장으로 설명할 수 있다. 조건이나 주제가 겹쳐 복잡해지면 문장을 나누되 인과관계는 유지하라.

'안정성 강화', '운영 효율 제고', '정합성 확보', '처리 고도화'로 설명을 끝내지 마라. 실제로 무엇을 덜 하게 됐고 어떤 상황에서 어떤 동작을 하는지 써라. 원문에 관찰 결과나 수치가 없으면 성과를 확정하거나 숫자를 만들지 마라.

'통행증', '청소 작업'처럼 새 별칭을 외워야 하는 비유는 피하라. 예를 들어 '인증 정보(passport)'라고 쓰고 누구를 대신한 요청인지 나타내는 정보라고 짧게 설명하라. 기술 용어를 쉬운 말로 바꾸면서 의미 범위를 넓히거나 좁히지 마라.

'이 문서의 단어들', '최신 빌드에 추가된 것'보다 '주요 용어', '주요 변경 사항'처럼 자연스러운 제목을 써라. '내부 API 키를 주기적으로 갱신합니다'처럼 내용을 알 수 있는 제목도 사용하라. 제목까지 항상 문장형으로 늘릴 필요는 없다.

'함께 살펴볼까요?', '놀랍게도', '여정', '단순한 X를 넘어 Y' 같은 장식, 과장, 반복 질문을 습관적으로 넣지 마라. 개발 블로그의 저자 인사, 농담, 채용 문구를 업무 문서에 가져오지 마라. 원문에 없는 실험, 대안 비교, 성능 개선, 개발자의 고민을 지어내지 마라.

## 설명을 자연스럽게 이어가기

본문은 동료에게 설명하듯 담백한 '합니다'체로 쓰되, 변경 보고만 이어지지 않도록 문장 역할을 구분하라. 사용 기능은 '확인할 수 있습니다', 구현 변경은 '확인하도록 했습니다', 기존 방식의 결과는 '확인하게 됩니다'처럼 실제 의미에 맞게 서술하라. SKILL.md의 끝맺음 기준을 함께 적용하라.

문장별로 사실과 간결함을 점검한 다음, 문단 전체를 이어 읽는 두 번째 검토를 하라.

- 앞 문장에서 제기한 문제나 조건에 다음 문장이 답하는지 확인하라. 이유와 결과를 독자가 다시 조합해야 할 정도로 문장을 잘게 나누지 마라. 한 문장에 하나의 중심 내용을 담는다는 이유로 서로 연결된 동작과 효과까지 분리하지 마라. 길이를 획일적으로 맞추지 마라.
- 원문에 있는 실제 상황과 사례를 활용해 동작을 설명하라. 필요하면 간단한 가정을 예시라고 밝혀 사용하되, 실제 경험·실험·운영 결과로 제시하지 마라.
- '추가했습니다·수정했습니다'가 반복되면 기능을 쓰는 사람의 관점이나 현재 동작으로 설명할 부분을 찾아라. 단어만 바꾸지 말고 문장의 목적을 다시 정하라. 원문에 있는 실제 배포 상태와 시제는 보존하라.
- 한자어를 풀어도 어색한 단어 조합이 남을 수 있다. '문서 처리 기능을 넓혔습니다'는 '처리할 수 있는 문서 형식을 늘렸습니다'로, '실패하는 제약'은 '이 조건에서는 실행에 실패한다는 점'처럼 문맥에 맞게 고쳐라. 이 과정에서 확정된 실패를 가능성으로 약화하지 마라.
- 변경의 중요도에 맞게 분량을 조절하라. 인증 방식 변경에는 원인·동작·배포 조건이 필요할 수 있지만, 파일 필터 수정은 한 문장으로 충분할 수 있다. 모든 항목을 같은 틀과 길이에 맞추지 마라.
- '중간 파일 자동 정리' 같은 자연스러운 명사형 제목은 허용하라. 본문에서는 조사와 동사를 갖춘 설명을 쓰되 제목까지 모두 문장형으로 늘리지 마라.

예시: '이번 버전부터 내부 API 키를 기본 6시간마다 새로 발급하는 방식으로 변경되었습니다. 키를 바꾸는 시점에도 진행 중인 요청을 처리할 수 있도록 직전 키는 1시간 동안 함께 허용합니다. 다만 외부 연동에서 고정된 키를 계속 사용하면 해당 키의 허용 기간이 지난 뒤에는 인증에 실패하게 됩니다.' 이는 동작·의도·조건에 따른 결과를 연결하는 예시이며, 다른 문서에 적용할 때 주기와 유예기간을 그대로 가져오지 마라.

## 변경 내용과 효과를 한 문장으로 연결하기

변경한 동작이 문제를 해결한 관계가 원문에 있고 문장이 복잡하지 않다면 '~하여 ~문제를 해결했습니다'처럼 연결하라. 핵심 동작을 먼저 알리면서 효과까지 한 번에 이해하게 하라. 뒤에 '이를 해결하기 위한 변경입니다'를 덧붙여 같은 변경을 다시 설명하지 마라. 실제로 별도의 의도나 배경을 설명해야 할 때는 문장을 나눌 수 있다.

- 기존: '이번 버전부터는 실행에 성공하면 중간 파일을 바로 삭제합니다. 실행 후에도 파일이 쌓이는 문제를 해결하기 위한 변경입니다.'
- 개선: '이번 버전부터는 파이프라인 실행에 성공하면 중간 파일을 바로 삭제하여 실행 후에도 스토리지에 파일이 쌓이는 문제를 해결했습니다.'

이 예시는 사용자가 선호한 설명 방식이다. 다른 문서의 운영 사실로 옮기지 마라. 원문에 해결 의도만 있다면 '해결했습니다'로 확정하지 말고 '~문제를 줄이기 위해 ~하도록 했습니다'처럼 의도 수준을 유지하라. 변경과 효과가 관계없거나 조건이 복잡하면 억지로 합치지 마라. 단순 조건의 '성공하게 되면'은 '성공하면'으로 줄일 수 있지만 '~하게 됩니다' 등 자연스러운 결과 표현을 일괄 삭제하지 마라.

## 시제와 수동 표현을 따로 점검하기

- 과거 문제: '기존에는 인증 정보가 만료되면 실행에 실패했습니다.'
- 완료한 변경: '이번 버전에서 만료 여부를 확인하는 로직을 추가했습니다.'
- 해당 버전의 동작: '각 노드는 인증 정보를 사용하기 전에 만료 여부를 확인합니다.'
- 현재 진행: '파서를 별도 프로세스로 분리하는 작업을 진행하고 있습니다.'
- 미확정 상태: '배포 일정은 아직 정해지지 않았습니다.'

각 문장이 어느 시점의 사실인지 확인하라. 능동형은 누가 무엇을 하는지 명확하게 만드는 수단이며 모든 '~되다'를 없애는 규칙이 아니다. '포함되어 있습니다' 같은 상태 서술을 과거의 배포 완료로 바꾸지 마라. 출처가 과거 문서라면 기준 날짜를 유지하라.

## 전달하기 전에 확인하기

제목과 첫 문단만으로 문서의 주제와 범위를 알 수 있는지 확인하라. 각 절이 핵심과 조건을 먼저 알려주는지, 제목과 첫 문장이 불필요하게 반복되는지, 문단마다 새 정보를 주는지, 어려운 명사를 연달아 쓰지 않았는지, 동작의 주체가 분명한지 살펴라. 짧게 고치면서 기본값·단위·조건·제약·불확실성·이력 정보를 지우지 않았는지 원문과 대조하라. 문체를 다듬은 것과 실제 구현을 검증한 것을 구분하라.

한국어 표기·쉼표와 문장 성분의 호응은 SKILL.md에서 연결한 한국어 지침으로 검토하라.

요청한 완성 문서를 제공하고, 요청하지 않은 편집 과정 설명은 길게 붙이지 마라. 전체 문서 작업은 적절한 문서 파일로 제공하고, 사용자가 특정 문단만 요청하면 그 부분만 제공하라. 파일을 만들 때는 현재 환경의 저장 규칙을 따르라.
